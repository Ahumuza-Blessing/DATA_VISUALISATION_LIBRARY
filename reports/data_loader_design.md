Phase 1 Report: DataLoader Design and Setup

1. Introduction

The purpose of Phase 1 was to establish the initial design and file structure for the DataLoader module of the Data Visualization Library developed using C++.

The DataLoader is an important component of the library because it will provide data to subsequent modules responsible for preprocessing, statistical analysis, and visualization.

2. Personal Objectives this week

The objectives of this week were:

- To establish the development environment for the DataLoader module.
- To organize the work within a dedicated Git feature branch.
- To identify the responsibilities of the DataLoader.
- To create the initial header and source files.
- To define the proposed public interface and internal data structures.
- To establish a foundation for implementation and testing in subsequent phases.

3. Development Environment and Version Control

The project repository was cloned from GitHub and opened in Visual Studio Code.

A dedicated feature branch named "feature/data-loader" was created and pushed to the remote repository. This allows DataLoader development to proceed independently of the main branch and supports collaborative development, code review, and integration.

The existing project structure was inspected to understand the intended roles of the "include", "src", "tests", "examples", and "reports" directories.

4. Design Decisions

4.1 Initial File Format

CSV (Comma-Separated Values) was selected as the initial file format to support because it is widely used for storing tabular data and can be generated by spreadsheet applications and many data-processing tools.

Support for additional formats may be considered in future development if required by the project.

4.2 Separation of Interface and Implementation

Two files were established for the module:

- "include/DataLoader.hpp": Contains the class declaration and public function declarations.
- "src/DataLoader.cpp": Reserved for the function implementations.

This separation improves organization, maintainability, and reuse by other components of the library.

4.3 Data Representation

The proposed internal representation uses:

- A vector of strings to store column headers.
- A two-dimensional vector of strings to store data records.

This representation allows the loader to store numerical and categorical values without immediately converting them into specific data types.

Data type conversion, missing-value treatment, and other cleaning operations will be handled during preprocessing.

4.4 Error Handling

The proposed "loadCSV()" function returns a Boolean value to indicate whether loading succeeded.

The implementation will need to handle situations such as a file that cannot be opened, an empty file, and malformed input. The precise handling of these cases will be established and tested during implementation.

5. Initial Class Interface

The DataLoader interface includes the following proposed functions:

- "loadCSV()": Loads records from a CSV file.
- "getHeaders()": Provides access to the column headers.
- "getRows()": Provides access to the loaded records.
- "getRowCount()": Returns the number of loaded records.

The internal data members are private to protect the class's internal representation from direct external modification.

The getter functions are designed to return constant references to avoid unnecessary copies of potentially large datasets.

6. Relationship with Other Modules

The DataLoader is intended to form the entry point of the library's data workflow.

The anticipated workflow is:

Data file → DataLoader → DataProcessor → Statistics → Plot generation → Rendering → Image export.

The DataLoader will focus on reading and organizing input data. The DataProcessor will be responsible for subsequent cleaning and transformation, while the statistics and plotting modules will operate on prepared data.

This separation of responsibilities is intended to improve modularity and simplify maintenance.

7. Current Progress

The initial design decisions have been established, and the header and source files have been created.

The header contains the proposed class interface and data structures. The source file has been reserved for the implementation.

CSV parsing, error handling, integration with other modules, and automated testing have not yet been completed.

8. Challenges and Considerations

The design must account for the fact that CSV fields may contain quoted commas, empty values, and other formatting details.

The team will also need to agree on how the DataLoader communicates errors and how its data representation aligns with the DataProcessor interface.

These considerations will be addressed during implementation and testing.

9. Conclusion

Phase 1 established the initial design and organizational foundation for the DataLoader module.

The proposed interface separates data loading from preprocessing and visualization, supporting the project's objective of creating a reusable C++ library.

The next phase will focus on implementing CSV loading, handling file-reading errors, and verifying the module through appropriate tests.
